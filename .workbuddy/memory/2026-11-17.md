# 2026-11-17

## 内盘（pump.fun 曲线）支持非 WSOL 池子，默认走 Jupiter

需求由来：pumpfundata 采集侧不过滤非 WSOL 池，但查询侧 `quoteKind:"sol"` 过滤；
交易侧内盘只用 `pfSwap.buy/sell` 直连曲线（SOL 硬编码），非 WSOL 池发不出去。

关键事实：**pump.fun 曲线只有 SOL 计价**（bondingCurveAccount 无 quote 字段），
所谓「内盘非 WSOL」= 该 token 已有 USDC/其它 SPL 计价的 Pump AMM 池。

改动：
- `app/libs/pool.js` 新增 `getPumpPoolsWithQuoteInfo()`：列出 token 全部 Pump AMM 池
  并标 `isNativeQuote`，无 WSOL 池不抛错（区别于 `getPoolsWithPrices` 的 NO_WSOL_PUMP_POOL）。
- `app/service/executeSwap.js#checkToken`：
  - 外盘 routeInfo 增加 `useJup/isNativeQuote/amm`，PoolStore 同步写 pool。
  - 新增内盘分支：`amm === "pump"` 时扫池子，只有非 WSOL 池才判 `useJup`；
    结果做 5 分钟进程内缓存（`pumpQuoteCache`），避免每次 checkToken 都 getProgramAccounts。
  - `ExecuteToken` 落 `useJup` / `quoteMint`；更新时若 routeInfo 为空则不覆盖旧 useJup（宁可继续走 jup）。
- `app/model/executeToken.js` 加 `useJup` / `quoteMint` 字段。
- `app/service/pumpfun.js`：`getJupRouteInfo()` 读标记；买卖两侧 useJup 时走
  `jupSwap.getBuyInstructions/getSellInstructions`，SOL 计价进出；预取报价、带
  lookup table 编译、jup 买入额外 simulate 一次；走 jup 时跳过 Axiom 曲线预计算。
- 新增 `scripts/pumpfun-jup-route-check.js`（7 项离线自检，全通过）。

约定：
- 内盘滑点内部是 bps（`SLIPPAGE_BASIS_POINTS=5000n`），Jupiter 要 0~1 小数，
  一律用 `getWalletSlippageFraction()` 转换；`pumpAMM.js` 那边是小数口径，勿混。
- 支付币默认 SOL；`wallet.buyAmount` 语义不变（SOL 计价）。

## run/pfd-cache 占盘：补全量清理

根因：清理只有 `ensureRange` 里「下完就删」一条路径（`manager.js` 的 dropHour），
**没有全量兜底扫描**。所以改配置前下载的旧文件、崩溃留下的 `.part`、入库失败的 slot
永远清不掉（实测本地留着 8 天前的 `2026-11-09/12.parquet`）。

改动：
- `app/libs/pfd/store.js` 新增 `pruneCache({ keepHours, dryRun, all })`：
  按**数据时间**（目录名 + 小时）判过期，`.part` 按 mtime 留 1 小时余量，
  删完顺手清理空日期目录；`all:true` 全清。
- `app/libs/pfd/manager.js` 新增 `pruneDiskCache()`，在 `dailyIngest` 采集结束后调用，
  结果写进 `lastIngest.cachePruned` 并打日志。
- 新增 `scripts/pfd-cache-prune.js`：不依赖 egg，默认 dry-run，`--apply` 才真删，
  支持 `--keep-hours N` / `--all`。

顺带修掉两个既有问题：
- `fs.rm(dir, {recursive:false})` 对目录报 EISDIR，空目录删不掉 → 改 `fsp.rmdir`。
- `scripts/pfd-integration-check.js` 假模型缺 `findOne`（`_explainEmpty` 直接崩），
  且 `createDay: 5` 写死，缓存文件一过期就假失败 → 改成按缓存小时推算窗口。

容量口径：单小时 parquet 实测约 17MB。`PFD_CACHE_KEEP_HOURS` 默认 72，
即稳态约 3 天 × 24h × 17MB × 2 交易所 ≈ 2.4GB；超过这个量就说明有残留。
设 0 = 不清理（历史残留的常见原因）。

## 修正：pump.fun 曲线本身可以非 SOL 计价（6063 UnsupportedQuoteMint）

之前的判断「曲线只有 SOL 计价」是**错的**。报错实例：
`DrJPPRpJ...pump` buy 0.01 → `AnchorError: Unsupported quote mint (6063)`。

真相：新版 pump.fun 允许用别的币当计价单位（另一个 pump 币 / 稳定币）。
该币曲线账户 166 字节，`quote_mint = SPCXxcqXj6e5...`（用另一个 pump 币计价），
虚拟储备 24,460,093 是计价币的最小单位，不是 lamports。

为什么旧代码看不出来：`app/libs/pumpfun/bondingCurveAccount.js` 只解前 81 字节，
把 offset 16 的 `virtual_quote_reserves` 叫成 `virtualSolReserves`，也读不到 `quote_mint`。

新布局（结构体 158 + 8 字节 discriminator = 166，参考 @pump-fun/pump-sdk 4.x）：
`+8 vt, +16 vQuote(原 vSol), +24 rt, +32 rQuote, +40 supply, +48 complete,
+49 creator(32), +81 isMayhemMode, +82 isCashbackCoin, +83 quote_mint(32)`
**SOL 曲线的 quote_mint 是全零 pubkey**；老曲线物理上只有 81 字节，必须做长度守卫。

改动：
- 新增 `app/libs/pumpCurve.js`：`decodeCurve` / `getCurveQuote`（5 分钟进程内缓存、
  失败不缓存、老布局守卫）、`curvePda`、`isSolQuote`（全零 / WSOL / Token-2022 native）。
- `executeSwap#checkToken` 内盘分支改为**以曲线 quote_mint 为权威判据**：
  非 SOL → 落 `routeInfo.useJup` + `quoteMint`；曲线缺失/已毕业才退回扫 Pump AMM 池。
  副作用是正常 SOL 币不再每次 `getProgramAccounts`，反而更快。
- `pumpfun#getJupRouteInfo`：DB 没标记时兜底读一次曲线（覆盖已入库的旧 token），
  命中就回填 `useJup` 到库。
- 买卖两侧沿用既有 jup 分支，自动生效。

验证：Jupiter 能路由这类币 —— `SOL→USDC→SPCX`(Whirlpool，带
restrictIntermediateTokens=true 时) `→该币曲线(Pump.fun)`，最后一跳 ammKey 就是曲线 PDA。

遗留：mayhem 模式（isMayhemMode）未做特殊处理；若将来要在链上直连这类曲线，
需要实现 buy_v2/buy_v3 + quote 账户（quote_mint / 曲线 quote ATA / 用户 quote ATA /
可能的 QuoteControl PDA），成本较高，目前用 jup 绕过。

## 坑：Jupiter 多跳交易 duplicate instruction

`failed to simulate transaction: invalid transaction: Transaction contains a
duplicate instruction (1) that is not allowed`

Solana 交易清洗规则不允许同一笔交易里出现两条「程序 + 账户 + data 完全相等」的指令。
Jupiter 的 `/swap-instructions` 在**多跳路由**下会把中间币的 `createIdempotent` ATA
同时放进 `setupInstructions` 和 `otherInstructions`，直接拼进 tx 就在模拟阶段挂掉
（这笔是 SOL→USDC→SPCX→曲线，正是多跳）。

修复：
- 新增 `app/libs/txInstructions.js#dedupeIdempotentInstructions`：
  去掉完全重复的指令。**一律删**，因为重复本身就让交易无法上链，保留没有任何意义；
  只对非幂等程序的重复额外打日志（`unexpected`）方便复查。
- `pumpfun.js` 买卖的 jup 分支：编译前统一过一遍 `dedupeIxs`。
- 顺带去掉自己追加的 `setComputeUnitLimit`：Jupiter 在
  `dynamicComputeUnitLimit: true` 下自带这条，我们的只会被覆盖，还多一个撞重复的机会。
  优先级费 `setComputeUnitPrice` 仍用钱包配置的。

测试：`scripts/pumpfun-jup-route-check.js` 扩到 17 项（去重的 4 个用例 +
jup 分支不再追加 CU limit 的静态断言）。

注：沙箱里直连 lite-api.jup.ag 会超时（只有 RPC 域名通），只能用 WebFetch 验证 quote。

## 坑：Jupiter 多跳交易超 1232 字节

`failed to simulate transaction: base64 ... too large: 1656 bytes (max: encoded/raw 1644/1232)`

三跳路由（SOL→USDC→SPCX→曲线）账户太多，Jupiter 没给 ALT 时顶到单笔上限。
实测量只超约 10 字节，所以砍掉自己加的指令就够。

修复：`app/libs/txInstructions.js#compileWithSizeFallback`
按体积逐级尝试，返回第一个放得下的版本：
  1. 原样
  2. 去掉本进程加的 ComputeBudget（Jupiter 自带 CU limit）
  3. 再去掉 tip
  4. 只去掉 tip
装不下就抛错并带上每种方案的体积，便于判断是不是路由本身太大。
`tipDropped` 为真时调用方要补一笔独立的 tip 交易，否则 jito bundle 会被拒
（pumpfun 买卖两侧都已补）。

测试：`scripts/pumpfun-jup-route-check.js` 扩到 21 项。

下一步可用的手段（暂未做）：给 jup 请求打开 `useSharedAccounts: true`，
它会把账户合并进共享账户 PDA，能显著缩小多跳路由的交易体积。

## 坑：Jito bundle "bundles cannot lock any vote accounts"

现象：两笔 jup 买入都模拟通过，发 bundle 时 QuickNode/Jito 返回
`{"code":-32602,"message":"bundles cannot lock any vote accounts"}`。

含义：bundle 里的交易**写锁了 vote 账户**，Jito 一律拒绝。
已排除的可能：
- Jito 那 8 个 tip 账户全部 owner = `T1pyyaTN...`（小费分发程序），不是 vote 账户；
- 我们自己注入的固定地址（BUYBACK / FOMO 收款）不在 jup 路径上。
推断：来自 Jupiter 路由命中的池子。某些池子（humidifi 系、GoonFi 之类）
把 vote 账户当**反 bundle 标记**塞进账户列表，交易跟着带上就没法打包。

处理（降级而非阻断）：
- `app/libs/txInstructions.js#findVoteAccounts`：解析 staticAccountKeys + ALT 里的
  地址，批量 `getMultipleAccountsInfo` 判 owner 是不是 Vote 程序，返回命中的地址。
- `pumpfun.js` 买卖的 sendBundle 外面包一层：错误信息含 "vote account" 时，
  先定位并打印地址，再降级逐笔 `sendTransaction`（牺牲 bundle 原子性换能成交）。
- 想恢复走 bundle：把日志里定位到的 DEX 加进 `JUPITER_EXCLUDE_DEXES` 重试。

另注：`isDevelopmentEnvironment()` 判定 local/dev/development。他们服务器日志里
出现了 "Pump.fun simulation success"，说明 `config.env` 是 local ——
每笔内盘买入都会多一次 simulate 往返，且 skipPreflight=false。
生产应设 `EGG_SERVER_ENV=prod`。

### 已定位：标记账户 = J1to1yuf...（Jito1 实验性 vote）

实测日志：`交易里含 vote 账户 J1to1yufRnoWn81KYg1XkTWzmKjnYSnmE2VY8DGUJ9Qv`。
就是 humidifi 系暗池的反 bundle 标记。**路由选中的池子天生进不了 bundle**，
不是构造问题。

解决思路：换一条不含该标记的路由。
- `libs/jup.js`：`getQuote(..., options.excludeDexes)` 支持按调用覆盖排除列表；
  买卖指令都回传 `routeLabels`（来自 quote.routePlan）。
- `pumpfun.js#rebuildJupWithoutVoteMarkers`：买入前用 `buildProbeTx` 编译一次只读探针，
  `findVoteAccounts` 命中就「排除除 Pump.fun 外的全部 DEX」重建一次，再探一次确认干净。
  重建后无路由 / 仍带标记 → 回退原路由，交给发送阶段的逐笔降级。
- 结果缓存 2 分钟（`jupRouteMarkerCache`），避免每笔都多一次 RPC + 多轮报价。
- 已验证：排除 GoonFi/BisonFi 后该币仍有 `Whirlpool SOL→SPCX` + `Pump.fun SPCX→币` 的路由，
  报价差约 0.7%（20.1e10 vs 22.1e10 outAmount）。换 bundle 准入，值。

未做：卖出侧目前只有降级兜底，没做排除重建。

### 结论：pump 币计价曲线在 Jupiter 上无法进 bundle

实测 `[jup] route Whirlpool > GoonFi V2 > Pump.fun`，排除掉
`Whirlpool,GoonFi V2` 后重建**仍带** `J1to1yuf...`。
=> 标记来自 **Pump.fun 那一跳本身**（exotic quote 曲线的路由），排除任何 DEX 都去不掉。

即：**Jupiter + bundle 对这类币不可兼得**。可选路线：
1. 接受逐笔（`batchBuyToken` 的降级逻辑，能成交但丢原子性/抗夹）；
2. `PUMP_REQUIRE_BUNDLE=true` 直接拒单，宁可错过；
3. 原生实现 pump 的 `multi_hop_swap`（SOL→计价币→曲线，单指令，不带标记）——
   需要新的 IDL/账户布局，工作量和风险都大，尚未做。

代码侧：
- `rebuildJupWithoutVoteMarkers` 改成最多 3 轮收敛（每轮把当前路由里除 Pump.fun
  外的 DEX 全部排除），排不动就明确打印「已无可排除的 DEX」，并缓存
  `{ impossible: true }` 2 分钟避免重复烧报价。
- 新增 `PUMP_REQUIRE_BUNDLE` 开关：为 true 时 bundle 被拒直接抛错，不降级。

### 自己踩的坑：缓存把探测也跳过了

两次同样参数，第一次 bundle 成功、第二次被拒。原因：
- 第一次路由 `Whirlpool > Pump.fun`（干净）→ 探针通过 → 缓存 `excludeDexes: ""`；
- 第二次 Jupiter 换成 `BisonFi > Byreal > Pump.fun`（带标记），但缓存命中时
  我的判断 `cachedExclude === undefined` 为 false（`""` 不是 undefined），
  **整个探针被跳过**，带着标记直接发 → 被拒。

教训：**Jupiter 的路由几秒内就会变，缓存绝不能跳过探测**。
现在缓存只复用「排除哪些 DEX」，每笔都探一次；另外缓存里的排除项如果
把路由排没了，会自动退回默认路由重取（否则一个过期缓存能让买单直接失败）。
自检 28 项，新增「缓存只复用排除项，不能跳过探测」防回归。
